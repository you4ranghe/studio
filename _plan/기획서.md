## 0. 제품 정의와 차별점

> **"돌잔치·청첩장·행사 퀴즈를, 폼만 채우면 HTML 파일 하나로 뽑아주는 서비스"**

모바일 청첩장 업체는 이미 포화 상태입니다. 같은 것을 만들면 이깁니다. 이 프로젝트가 이미
증명한 차별점은 하나입니다 — **결과물이 서버가 아니라 사용자 손에 있는 파일**이라는 것.

- 업체가 망해도 남습니다 (기존 청첩장 서비스의 최대 불만: 1년 뒤 링크 사망)
- **행사장 와이파이 없이 프로젝터에서 돌아갑니다** ← 퀴즈·식순 카테고리에서 압도적
- 원하면 사용자가 직접 열어서 고칠 수 있습니다

카피는 "예쁜 청첩장"이 아니라 **"파일로 소유하는 초대장"** 으로 잡습니다.

## 1. 핵심 설계 판단 ① — 템플릿의 정의

여기서 실패하면 템플릿 3개째부터 코드가 무너집니다.
**템플릿은 "완성된 HTML"이 아니라 "렌더러 + 스키마" 한 쌍**으로 정의합니다.

```
templates/dol-quiz/
├─ schema.json      ← 사용자가 입력할 필드 정의 (폼이 여기서 자동 생성됨)
├─ renderer.html    ← 현재 slides.src.html. 데이터 자리에 __DATA__ 마커 하나만
├─ sample.json      ← 데모·초기값 (지금의 채원이 데이터)
├─ assets/          ← 폰트, 효과음
└─ meta.json        ← 이름, 카테고리, 썸네일, 가격, 예상 소요시간
```

빌드는 단순합니다. `renderer.html`의 `__DATA__` 자리에 사용자 JSON을 꽂고, 폰트·에셋을
base64로 심어 파일 하나로 뱉습니다. **지금 `build.ps1`이 폰트에 하는 일과 정확히 같습니다.**
즉 이미 만들어 둔 것이 그대로 1번 템플릿이 됩니다.

> **규칙 하나만 지키면 됩니다 — 렌더러는 자기 데이터를 하드코딩하지 않는다.**
> `slides.src.html`에서 `SLIDES` 배열만 밖으로 빼면 1번 템플릿이 완성됩니다.

## 2. 핵심 설계 판단 ② — 폼은 만들지 않고 생성한다

템플릿마다 입력 폼을 새로 짜면 템플릿 5개에서 개발이 멈춥니다.
**`schema.json` → 폼 자동 생성** 구조로 갑니다. 필드 타입은 아래로 고정하고,
이걸로 표현이 안 되면 폼이 아니라 템플릿을 바꿉니다.

| 타입 | 용도 | 예 |
|---|---|---|
| `text` / `longtext` | 짧은 글 / 인사말 | 아이 이름, 초대 문구 |
| `date` / `datetime` | 날짜 | 돌잔치 일시 |
| `number` | 숫자 | 몸무게, 키 |
| `image` | 사진 (자동 리사이즈·압축) | 대표 사진 |
| `select` / `toggle` | 옵션 | 테마 색, 음악 on/off |
| `place` | 장소 (주소 + 지도) | 예식장 |
| **`repeater`** | **반복 블록** | **퀴즈 문항, 갤러리, 타임라인** |

`repeater`가 절반입니다. 퀴즈 10문항, 사진 갤러리, 식순, 계좌 목록이 전부 repeater 하나로
처리됩니다. 여기에 힘을 몰아줍니다.

```json
{
  "id": "quiz",
  "type": "repeater",
  "label": "퀴즈 문항",
  "min": 5, "max": 20, "recommended": 10,
  "itemLabel": "Q{index}",
  "fields": [
    { "id": "question", "type": "text", "label": "문제", "maxLength": 40,
      "hint": "화면에 두 줄까지 예쁘게 들어갑니다" },
    { "id": "options", "type": "repeater", "min": 2, "max": 5,
      "fields": [{ "id": "text", "type": "text" }] },
    { "id": "answer", "type": "select", "source": "options" }
  ]
}
```

## 3. 화면 구조 (IA)

```
랜딩 ──▶ 템플릿 갤러리 ──▶ 템플릿 상세(실물 데모) ──▶ 에디터 ──▶ 완성 화면 ──▶ 다운로드/공유
                                                      ▲
                                                  내 프로젝트
```

여섯 화면이면 충분합니다. 더 만들면 관리가 안 됩니다.

| 화면 | 핵심 |
|---|---|
| **① 랜딩** | 설명 대신 결과물. 히어로에 실제 템플릿이 돌아가는 iframe. CTA는 "샘플 열어보기" |
| **② 갤러리** | 카테고리(돌잔치 / 결혼 / 생일·환갑 / 행사 퀴즈) × 카드. 카드에 **소요시간("입력 5분")과 결과물 형태("HTML 1개, 오프라인 재생")** 를 박습니다 |
| **③ 템플릿 상세** | 진짜 결과물을 새 탭에서 풀스크린으로. 스크린샷 나열은 안 됩니다 — 퀴즈는 넘겨봐야 매력이 전달됩니다 |
| **④ 에디터** | 제품의 전부. §4 참고 |
| **⑤ 완성 화면** | 다운로드 + 공유 링크 + **사용법 안내**(카톡 전송법, 프로젝터 띄우는 법, iOS 주의). 이 안내가 CS를 절반으로 줄입니다 |
| **⑥ 내 프로젝트** | 재편집·재다운로드. 결혼·돌잔치는 무조건 여러 번 고칩니다 |

## 4. 에디터 설계

```
┌──────────┬─────────────────────────┬──────────────────────────┐
│ 스텝     │  폼 (현재 스텝만)        │  실시간 미리보기          │
│ ● 기본정보│  ┌───────────────────┐  │  ┌────────────────────┐  │
│ ● 인사말 │  │ 아이 이름  [채원]  │  │  │                    │  │
│ ○ 퀴즈   │  │ 생일  [2025-08-15] │  │  │   (iframe 실물)     │  │
│ ○ 디자인 │  │ 대표사진  [ + ]    │  │  │                    │  │
│ ○ 음악   │  └───────────────────┘  │  └────────────────────┘  │
│          │      [이전]  [다음]      │  [PC][모바일]  [새 탭]   │
└──────────┴─────────────────────────┴──────────────────────────┘
```

지켜야 할 원칙 다섯 개:

1. **로그인 없이 바로 편집 시작.** 익명 프로젝트를 localStorage + 서버 임시 저장으로 만들고,
   **다운로드를 누를 때 처음 로그인**을 요구합니다. 로그인을 앞에 두면 여기서 70%가 나갑니다.
2. **빈 폼을 절대 보여주지 않습니다.** 샘플 데이터가 채워진 상태로 시작해 사용자는 "고치기"만
   합니다. 백지 공포가 최대 이탈 원인입니다.
3. **미리보기는 iframe + postMessage로 데이터만 갱신.** 입력할 때마다 iframe을 리로드하면
   퀴즈가 1페이지로 되돌아가서 못 씁니다. 렌더러에 `applyData(json)` 하나만 노출시키면 됩니다.
4. **자동 저장 + 되돌리기.** 저장 버튼 없음. 우상단에 "방금 저장됨"만.
5. **글자 수는 막지 말고 경고합니다.** 지금 `qSize`/`optSize`로 수동 조절하던 것을, 렌더러가
   길이에 따라 자동 축소하게 바꿉니다. 사용자에게 폰트 크기를 묻지 마세요.

스텝은 **5개 이하**로 쪼갭니다. 한 화면에 30개 필드를 세로로 늘어놓으면 완성률이 반토막 납니다.

## 6. 산출물 정책 — 실전 함정

지금 `index.html`이 **6MB**입니다. 폰트 1.7MB + 음악 3MB. 이대로 팔면 이런 CS가 옵니다.

- "카톡으로 안 보내져요" (용량)
- **"아이폰에서 빈 화면이에요"** ← `WBS.md` §5에 이미 기록된, 구조적으로 못 고치는 문제
- "열리는 데 오래 걸려요"

그래서 결과물을 **3종으로** 냅니다.

| 형태 | 내용 | 용도 |
|---|---|---|
| **경량 단일 HTML** | 폰트 **서브셋**(입력된 글자만), 이미지 리사이즈, 음악 링크 | 기본. **1.7MB → 100KB 이하** |
| 풀 패키지 ZIP | 음악·원본 이미지 포함 | 오프라인 프로젝터 발표용 |
| **공유 링크** | 서버 호스팅 (`share.도메인/a1b2c3`) | **모바일 배포는 사실상 이것만 답** |

> **공유 링크는 부가 기능이 아니라 필수입니다.** 아이폰이 로컬 HTML을 못 여는 이상,
> "파일 다운로드"만 파는 상품은 청첩장 카테고리에서 성립하지 않습니다.
> 파일은 "소유권", 링크는 "배포 수단"으로 포지셔닝하고 **둘 다 줍니다.**

## 7. 빌드는 서버에서

브라우저에서 조립하는 것도 가능하지만, 서버를 권합니다.

- **렌더러 소스가 통째로 유출되지 않습니다.** 클라이언트 빌드면 무료 사용자가 개발자도구로
  템플릿 전체를 가져갑니다. 유료 상품에서는 치명적입니다.
- 폰트 **서브셋·이미지 최적화**는 서버여야 제대로 됩니다 (§6의 100KB 근거)
- 공유 링크 호스팅과 어차피 같은 인프라입니다
- 워터마크 제거를 클라이언트에서 결정하면 우회됩니다

API는 셋이면 충분합니다.

| API | 역할 |
|---|---|
| `POST /api/projects` | 프로젝트 저장 (익명 포함) |
| `POST /api/build` | HTML 생성 → 파일 URL 반환 |
| `GET /s/:slug` | 공유 링크 |

**스택**: Next.js + Vercel, Supabase(Auth·DB·Storage). 빌드는 서버리스 함수 하나.
템플릿은 DB가 아니라 **저장소 폴더**에 두고 git으로 버전 관리합니다 — 템플릿은 코드지
데이터가 아닙니다.

## 8. 데이터 모델

```
users        (id, email, ...)
templates    (id, slug, category, price, status)           ← 메타만
projects     (id, user_id|anon_key, template_id,
              template_version,        ← ★ 버전 고정
              data JSONB,              ← 사용자 입력 전체
              entitlement, share_slug, expires_at)
```

`projects.template_version`이 핵심입니다. 템플릿을 개선했을 때 **이미 결제한 사용자의 결과물이
바뀌면 안 됩니다.** 재편집 시 "새 버전으로 업그레이드할까요?"를 물어봅니다.

## 9. 템플릿 라인업과 출시 순서

1. **돌잔치 퀴즈** — 이미 완성품이 있고, 경쟁이 거의 없고, "오프라인 재생" 차별점이 가장 크게
   먹히는 카테고리
2. **돌잔치 초대장** — 같은 고객이 같은 시기에 둘 다 필요합니다. 번들로 묶기 좋습니다
3. **행사용 퀴즈 (회사 워크샵·송년회)** — 1번 렌더러를 테마만 바꿔 재활용.
   **B2B라 객단가가 개인보다 높습니다**
4. **모바일 청첩장** — 레드오션이라 마지막. 앞의 3개로 파이프라인이 검증된 뒤 들어갑니다

> 템플릿 3개까지는 같은 렌더러 계열로 갑니다. 스키마–폼 파이프라인의 구멍은
> 2번째·3번째 템플릿에서만 드러납니다.

## 11. 마일스톤

### M1 — 파이프라인 증명
`slides.src.html`에서 `SLIDES` 분리 → `schema.json` 작성 → 스키마 기반 폼 렌더러 →
iframe 실시간 미리보기 → 클라이언트 빌드로 다운로드.
**로그인·결제·서버 없이 퀴즈 템플릿 하나만 끝까지.**
여기서 "남의 데이터로 만든 결과물"이 실제로 예쁜지가 판가름 납니다.

### M2 — 서비스화
서버 빌드 이관, 폰트 서브셋, 이미지 업로드, 인증, 프로젝트 저장, 공유 링크, 갤러리·랜딩.

### M3 — 상품화
워터마크·entitlement, 결제 스텁, 2·3번 템플릿 투입으로 파이프라인 검증, 사용법 안내·FAQ.

### M4 — 성장
템플릿 확장, 카카오 공유 최적화, 후기 수집.
